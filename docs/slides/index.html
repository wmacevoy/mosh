MOSH, WITH PORT FORWARDING · FOR STUDENTS

A connection that
does not drop.

Close the laptop. Change buildings. Lose the Wi-Fi. Your work on the server is still there when you come back.

Why you want it · how to set it up · how it works · a relay of your own

Open with the experience everyone in the room has had: an ssh session that died and took a long-running job with it. This deck is about never having that happen again, and it takes about ten minutes to set up. Note up front that this is an unofficial, experimental build of mosh.

THE PROBLEM

ssh is a phone call.

YOU CLOSE THE LID

The call drops.

The terminal on the server ends, and what was running in it ends too.

YOU WALK TO CLASS

New Wi-Fi, new address.

The server is still talking to where you used to be.

THE WI-FI BLINKS

Frozen cursor.

You wait, give up, log in again, and try to remember where you were.

None of this is your fault. It is how one long connection behaves on a network that moves.

ssh carries everything over a single TCP connection. If that connection breaks for any reason, the session is gone. Laptops break it constantly: sleep, roaming between access points, a few seconds of lost signal.

THE PROMISE

Open the laptop.
Your terminal is exactly where you left it.

mosh keeps the session alive on the server and finds its way back to it by itself, from wherever you are.

This is the one sentence to remember. Demonstrate it live if you can: connect, close the lid for thirty seconds, open it, keep typing.

WHAT YOU GET

Four things, one session

TERMINAL

A shell that survives

Sleep, roaming and outages are a pause, not an ending.

WEB PAGES

The server’s ports, on your laptop

Run the site there; open it in your own browser here.

FILES

Copies that finish

Interrupted copies carry on where they stopped. A folder can be kept up to date.

AWKWARD NETWORKS

It finds a way through

Blocked on campus, or a machine behind a home router: it works it out without being asked.

Standard mosh gives you the first card only. This build adds the other three: port forwarding, file copying with mocp, and getting through networks and routers that would otherwise stop it.

SET IT UP · TEN MINUTES

Three steps, no administrator

1

Make ssh log in without a password

ssh-keygen -t ed25519 # Enter at each question
ssh-copy-id you@server # your password, one last time

2

Install on your laptop, then the same line on the server

curl -fsSL https://raw.githubusercontent.com/wmacevoy/mosh/master/scripts/install.sh | sh

3

Connect

mosh you@server

Linux and macOS. On Windows, use WSL and follow the Linux steps. Installs into your own home directory.

Step 1 is where people get stuck: mosh starts with ssh, and some features log in again in the background where nobody can type a password. Step 2 is one line, run twice: once on the laptop, once on the server (ssh in and paste it, or run it through ssh). Both ends need this build. Then close the lid and open it again to see the point.

THE COMMANDS YOU WILL ACTUALLY USE

Terminal, web page, files

Work on the server, and keep your work if the window closes

mosh you@server -- tmux new -A -s main

See the site that runs on the server at http://localhost:8080

mosh -L 8080:localhost:8080 you@server

Copy a folder of results to your laptop

mocp -r you@server:project/out .

tmux is optional but worth it: mosh keeps the connection, tmux keeps the work even if the terminal window itself is closed. The -L option works exactly as it does in ssh. mocp is scp with mosh's patience: a copy that is interrupted waits, and one that is killed carries on where it stopped when you run it again.

THE ONE PEOPLE LIKE MOST

Build there. Look here.

mocp --auto -r you@server:project/out ./out

It stays running

Every two seconds it looks for what is new or changed on the server.

Your copy follows

The plot, the PDF, the build output appear on your laptop as they are made.

Through anything

Lose the network and it waits. Nothing arrives half-written.

One way only, and it copies everything it is pointed at: aim it at the folder of results, not the whole project.

Leave this in its own terminal. It is one-way, from the source to the destination: edits made in the copy are not sent back. Add --delete to also remove files that disappear at the source. Changed files are sent whole.

HOW IT WORKS

Not a phone call. Two notebooks.

SSH

One connection, every byte in order

laptop

server

Break the line and the conversation is over. The server cannot tell “asleep” from “gone”.

MOSH

A copy of the screen at each end, and small sealed notes

laptop

server

Each note says “here is what changed”. Notes can be lost, late, or come from a new address. The next one catches the other end up.

Web pages and files need every byte, so this build runs a small reliable channel inside the same notes. When the network goes, it waits.

ssh uses TCP: one ordered stream. mosh uses UDP datagrams, each encrypted and authenticated, and synchronises the state of the screen instead of replaying a stream. That is why it does not care when your address changes or packets go missing. Port forwarding and mocp ride on a small TCP of mosh's own, carried inside those same datagrams.

WHEN THE NETWORK FIGHTS BACK

Four ways through, best first

1

Straight there

The normal case: the server has a public address.

2

Straight through the routers

Both ends behind home routers: they open a path between them.

3

Passed along by your relay

Routers that cannot be opened: a machine both can reach hands it on. Still fast.

4

Inside an ssh connection

Networks that block everything else. It works, but it is the phone call again.

You choose nothing. mosh tries them without being asked, uses the best that works, and keeps trying the better ones.

Standard mosh has only the first. If its UDP is blocked it sits at Connecting forever. This build falls back to ssh after three seconds, and from there looks for something better: a direct path through the NAT routers, or UDP by way of a relay. When you change networks it starts again from the top by itself.

1 · ASK

“Where do I appear to be?”

Each end asks a server outside. That question has a name: STUN.

2 · TELL

Swap addresses

Over the ssh connection they already have. Sealed with a fresh key.

3 · SEND, BOTH AT ONCE

Each router sees an answer

It sent something out, something came back. The path is open.

Two laptops in the same room skip the routers altogether and find each other on the local network.

This is called hole punching. It is the same technique video calls and Tailscale use. It fails on routers that give out a different outside address for every destination, which many phone networks and some campuses do. Then mosh uses the relay instead.

A RELAY OF YOUR OWN · OPTIONAL

One tiny cloud machine both ends can reach

IT INTRODUCES

“You appear to be here.”

So the two ends can find a direct path. After that it carries nothing.

IT PASSES ALONG

When no direct path exists

It hands each end’s traffic to the other. It cannot read any of it.

IT IS PRIVATE

A key only you have

Without the key it does not answer at all.

You need this only to reach a machine with no public address. For a course server, skip it.

A course server normally has a public address, and plain mosh reaches it. The relay is for the other case: your own machine at home or in a lab, behind a router that nothing outside can start a conversation with. The smallest instance any cloud offers is enough, because most of the time it only makes introductions.

YOUR RELAY ON AWS · STEP 2 OF 3

Install it, make a key, start it

# from your laptop
ssh -i mosh-relay.pem ubuntu@RELAY

# on the relay: install, and make the key that makes it yours
curl -fsSL https://raw.githubusercontent.com/wmacevoy/mosh/master/scripts/install.sh | sh
mkdir -p ~/.config/mosh
echo "MOSH_STUN_KEY=$(~/.local/bin/mosh-server stun-key)" > ~/.config/mosh/stun.env
chmod 600 ~/.config/mosh/stun.env

# what the service runs, now and after every reboot
~/.local/bin/mosh-server stun 60000

The handout has the short service file that starts it at boot (systemctl enable --now mosh-relay). Copy the key out of stun.env: your laptop needs it next.

mosh-server stun-key prints a new random key. mosh-server stun 60000 is the relay itself: with MOSH_STUN_KEY set it answers only requests that carry proof of the key, and passes traffic along only for them. The README gives a systemd unit that reads the key from stun.env and restarts the relay if it stops.

YOUR RELAY ON AWS · STEP 3 OF 3

Point your laptop at it, and reach home

On your laptop, once

# in ~/.bashrc or ~/.zshrc
export MOSH_STUN=RELAY:60000
export MOSH_STUN_KEY=your-key

On the machine at home, kept running

ssh -N -R 2222:localhost:22 \
    ubuntu@RELAY

It holds a door open: port 2222 on the relay now leads to the home machine’s ssh.

In ~/.ssh/config on your laptop

Host relay
  HostName RELAY
  User ubuntu

Host home
  HostName localhost
  Port 2222
  ProxyJump relay

Then

mosh --experimental-remote-ip=remote home

The first few seconds travel through the relay inside ssh. Then the two ends find each other and the session moves to a direct connection, or to UDP passed along by the relay if a direct one is impossible. mocp and -L work the same way with the same option. This arrangement is tested in a lab with real NAT routers, with a stand-in for the ssh hop; try it yourself before relying on it. The handout adds the IdentityFile and User lines.

BEFORE YOU RELY ON IT

What is tested, and what is not

TESTED ON EVERY CHANGE

Linux, macOS, Windows builds

Terminal sessions, forwarding, copies that resume, the ssh fallback.

A lab with two real NAT routers: a direct path found, a router that cannot be opened, an address that changes mid-session, two machines on one network, traffic passed along by a keyed relay.

Fuzzers and memory checkers on everything that reads from the network.

NOT YET

The real world

Home routers that are not Linux, phone networks, and campus networks.

The AWS steps and the jump-host arrangement, end to end with a real ssh.

The native Windows programs beyond starting up. Use WSL.

Any outside review: this is an unofficial, experimental build of mosh.

Be straightforward about this with students. The parts they use every day, the terminal, forwarding and copying, are the best tested. The relay and hole punching are new, are tested against real address translation in a lab, and have not yet met the variety of routers out in the world. When something cannot be done the session falls back to ssh; it does not fail.
